部门要为多个小程序提供同一套业务能力。一开始的做法是复制仓库：A 小程序一套、B 小程序一套，改一个公共组件要改四五遍，线上问题也会在不同仓库里反复出现。

SaaS 化的目标很明确：**页面和公共能力只维护一份，小程序之间的差异通过配置表达。**

## Shell 和 Coding 分开

我们把工程拆成两层：

- **Shell**：负责拉取项目配置、构建、上传和部署。它知道「这次要构建哪个小程序」，但不关心页面长什么样。
- **Coding**：承载所有页面、组件和分包代码，Vue 和 React 两条技术栈各一套。

公共能力再按「是否依赖框架」分成两层：不依赖框架的纯逻辑放 `shared`，依赖框架的放 `framework`。这样换技术栈时，`shared` 可以整体复用。

## 项目配置是唯一的差异来源

每个 AppId 对应一份项目配置，声明这个小程序有哪些页面、组件、分包和 tabBar：

```json
{
  "appId": "wx-xxxx",
  "pages": ["pages/home/index", "pages/order/index"],
  "subPackages": [{ "root": "packageA", "pages": ["detail/index"] }],
  "tabBar": ["home", "order", "mine"],
  "components": { "price": "components/price/variant-b" }
}
```

Shell 读取配置后生成路由和分包。同一个页面在不同小程序里需要不同实现时，用 `dynamic` 组件 + 配置化 props 替换，而不是在页面里写一堆 `if (appId === ...)`。

## 构建脚本承担脏活

多小程序构建的复杂度主要在脚本里：

- 按 AppId 隔离上传密钥，避免 A 小程序的密钥被用来传 B；
- 构建前做配置校验，缺页面、缺分包直接失败；
- 补一个 Taro 样式引用审计脚本，防止多端构建时样式漏引；
- 输出产物体积报告，超过阈值时提醒。

这些脚本不产生业务价值，但能省掉大量人工操作和「为什么这个端样式不对」的排查时间。

## 什么时候不该 SaaS 化

如果几个小程序的业务重合度不到一半，或者每个端都有完全独立的交互，强行 SaaS 化会让配置变成新的复杂度来源。我们判断的标准是：**公共部分是否稳定、差异是否可枚举**。两个条件都满足，才值得做底座；否则复制仓库反而更便宜。
