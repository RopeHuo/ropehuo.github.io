做 QA Agent 最容易踩的坑，是把所有东西都塞进工具里：打开页面是工具，找元素是工具，判断结果对不对也写成工具。做着做着，工具数量膨胀到几十个，模型每次都要在一堆相似的名字里挑，判断逻辑还固化在代码里，需求一变就得改代码发版。

我们做的这个测试智能体，接入了多类 AI 编码宿主。它最后收敛成一个很简单的分层：**重 Skill，轻 MCP**。

## 一条分界线：判断还是执行

拆之前先问一句：这件事需要「理解」吗？

- **需要理解**：测什么、这一步算不算通过、失败原因怎么归类、报告怎么写——放进 Skill，交给模型。
- **不需要理解**：打开页面、点击、填表、截图、运行 spec——放进 MCP，用 TypeScript 写死。

MCP Server 只保留无判断的机械动作。这样带来两个直接好处：

1. 工具数量可控，模型不需要在几十个工具里做选择；
2. 改判断只需要改 Skill 里的说明，不用改代码、不用发版。

## 稳定骨架 + 能力插件

Skill 层没有写成一个大而全的流程，而是「骨架 + 插件」：

- 骨架只声明少量命名挂载点，规定一次测试从哪里开始、到哪里结束；
- 红线、PRD / 用例 / 测试数据等外部上下文、泳道、报告归档，各自是独立插件；
- 新增一种能力，只需要加一个插件文件，再在注册表里加一行，骨架零改动。

插件化的收益在后续需求到来时才显现：改动范围被限制在一个文件里，不会牵一发动全身。

## 模式让系统自己选

用户不该先理解「盲探」和「生成」的区别。建会话前，系统会先做一次源码可映射性探测：

- 能读到被测页面的源码：走**生成**，产出可回归的 Playwright 用例；
- 读不到源码：走**盲探**，用真实交互去探索页面；
- 手里有老页面做参照：走**对照**，比较新旧两版的行为差异。

模式自动判定之后，用户只需要给一个页面地址，或者一段 PRD。

## 报告要能直接用

测试跑完不是终点，报告才是交付物。我们的报告是单文件：

- 每条用例标注来源：来自源码、PRD 还是测试用例；
- 按通过、失败、阻断、跳过等状态统计；
- 附增删改查生命周期矩阵；
- 用「必测白名单 vs 实际覆盖」做对账，差集直接列出来。

报告跑完会自动归档到团队存储，随时能翻。

```text
skills/qa-agent/
  SKILL.md            # 判断：测什么、怎么判、报告怎么拼
  plugins/
    redline.ts        # 红线
    context.ts        # PRD / 用例 / 测试数据
    report.ts         # 报告归档
mcp/
  tools/
    open.ts  click.ts  fill.ts
    screenshot.ts  run-spec.ts
```

## 体会

这类系统的难点从来不是「让模型点一下页面」。真正决定它能用多久的，是分层：把易变的部分放到模型能读、能改的地方，把稳定的部分沉到代码里。工具化只是手段，可维护性才是目标。
