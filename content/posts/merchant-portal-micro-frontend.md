这是一个商家后台，业务多、团队也多。改造前的问题很典型：所有页面挤在一个仓库里，一个团队要上线，得等所有人一起发版；技术栈也开始分叉，有的页面是 Vue，有的是 React。

最后的方案是 Portal 主应用 + 多个业务子应用：主应用只做壳，子应用分仓开发、独立发布。

## 双模式加载，而不是二选一

微前端方案选型时，micro-app 和 iframe 经常被拿来比较。我们的结论是：**都要，按团队和页面来分**。

- 内部团队开发的子应用，用 micro-app 加载，保留路由、主子通信和统一的路由体验；
- 外部团队提供的页面，用 iframe 做隔离，不要求他们适配我们的技术栈，也不让他们的全局样式污染主应用。

加载方式由后端下发的配置决定，前端统一处理 baseroute、路由前缀、加载完成与失败态。

## 主子通信先定契约

微前端最容易失控的地方是通信。我们的约定是：

- 主应用通过 `data` 向子应用下发用户等上下文；
- 子应用通过 `datachange` 回传事件，事件类型统一注册；
- 子应用不直接读主应用的 store，主应用也不去子应用里拿状态。

```text
主应用 data      → { user, permissions }
子应用 datachange → { type: 'navigate' | 'notify' | 'refresh', payload }
```

契约定死之后，子应用内部怎么实现是自由的，联调成本也可控。

## 菜单和路由交给配置

后台系统的菜单天然是配置驱动的。菜单由后端下发，主应用按应用注册路由，再映射到对应子应用，支持多级菜单和面包屑。新增一个子应用，主要是配置工作，而不是改主应用代码。

## 边界：壳只做壳

主应用只保留三件事：

1. 登录态与用户上下文；
2. 菜单、路由、布局这些框架能力；
3. 子应用的加载、失败兜底和埋点。

业务逻辑一律下沉到子应用。这个边界一旦模糊，主应用就会重新变成大泥球——只不过这次是「微前端的大泥球」。

## 一点反思

微前端解决的是组织和发布的问题，不是技术问题。如果几个团队本来就能一起发版，或者业务之间耦合很深，硬拆只会把一次函数调用变成一次跨应用通信。拆之前先想清楚：你要的是独立发布，还是只是想要一个更清晰的代码结构？后者用 monorepo 分层可能就够了。
